DDNet / QmClient 鸿蒙（HarmonyOS NEXT）移植可行性报告

评估将 DDNet/QmClient 游戏客户端移植到华为鸿蒙系统（手机 + PC）的技术可行性、工作量、风险与推荐路线。同时对比 C++ 原版移植与基于 ddnet-rs 用 Rust 重写两条路径，给出诚实判断。

结论总判 C++ QmClient 技术现状 ddnet-rs 技术现状 两条路径对比 鸿蒙平台能力评估 方案 A：C++ 移植路线图 方案 B：ddnet-rs 重写路线图 推荐决策

结论总判

中等偏高难度，但完全可行

两条路径均无不可逾越的技术障碍，但核心阻塞点不同：
C++ 路径阻塞在 SDL2 无鸿蒙后端；Rust 路径阻塞在 ddnet-rs 功能远不完整。

项目已有 Android 移植经验（JNI 桥接、触摸控制、GLES 渲染），鸿蒙 NEXT 支持 OpenGL ES 3.x / Vulkan / POSIX socket，很多基础设施可直接复用。

核心判断：如果目标是尽快在鸿蒙上玩到 DDNet，C++ 移植是唯一现实选择（2-3 个月出可玩版本）。如果目标是做一个长期独立维护的原生客户端，ddnet-rs 架构更适合鸿蒙，但需要 6-12 个月才能达到可用状态。

窗口 / 输入 / 音频 —— SDL2 深度耦合

SDL2 是整个项目的单一阻塞点。它负责：
  • 窗口创建 & OpenGL/Vulkan 上下文管理
  • 全部输入（键盘、鼠标、触摸 SDL_TouchFingerEvent、手柄 SDL_Joystick）
  • 音频输出（SDL_OpenAudioDevice）
  • 剪贴板、URL 打开、系统对话框
  • Android JNI 桥接（SDL_AndroidGetJNIEnv、SDL_AndroidGetActivity）
SDL2 目前没有 OpenHarmony / HarmonyOS 后端。这是 C++ 移植路径的最大工作量来源。

UI 系统

完全自绘，无框架依赖：

  • src/game/client/ui.h —— 核心 CUI 类（按钮、标签、滚动条、编辑框、列表框）
  • src/game/client/QmUi/ —— QmClient 增强系统（29 文件）：动画、布局、主题、表单、导航
  • 渲染直接走 IGraphics（quad + FreeType 文字），无平台 UI 工具包依赖
UI 系统是移植的优势点：自绘 UI 意味着不需要适配任何平台 UI 框架，触摸控制也已现成。手机端只需要调整布局和 DPI。

架构亮点

  • 90+ crate workspace：高度解耦，每个子系统独立 crate，替换/适配成本低
  • graphics-backend-traits：渲染后端抽象 trait，理论上可添加 GLES 后端
  • WASM 扩展系统：UI 模块、编辑器、游戏逻辑可动态加载
  • native-display 抽象：窗口管理已与渲染分离

关键缺陷

以下问题使 ddnet-rs 当前无法作为鸿蒙移植的可行起点：
  1. 功能远不完整：物理、碰撞、地图编辑器、服务器浏览、demo 回放、皮肤系统等大量核心功能仅有骨架或缺失
  2. 网络协议不兼容：QUIC vs 原始 UDP + 自定义快照协议，连不上现有 DDNet 服务器
  3. 渲染只有 Vulkan：无 OpenGL ES 后端，鸿蒙手机 Vulkan 支持参差不齐
  4. winit 同样无鸿蒙后端：与 SDL2 问题等价

两条路径深度对比

方案 A：C++ QmClient 移植

思路：在现有完整游戏基础上，只替换平台层（SDL2 → 鸿蒙原生 API），其余代码几乎不变。

  • 功能完整度：100%
  • 协议兼容：完全兼容
  • 鸿蒙适配量：~5,000-8,000 行新代码
  • 时间估算：2-3 个月出可玩版本
  • 最大风险：SDL2 鸿蒙后端需自写
  • 长期维护：与上游 DDNet 合并冲突

方案 B：基于 ddnet-rs 重写

思路：基于 ddnet-rs 的模块化架构，补齐功能 + 适配鸿蒙，构建原生 Rust 客户端。

  • 功能完整度：~30-40%
  • 协议兼容：不兼容（需重写网络层）
  • 鸿蒙适配量：~3,000-5,000 行新代码
  • 时间估算：6-12 个月（先补功能再适配）
  • 最大风险：ddnet-rs 不完整 + Rust 鸿蒙工具链
  • 长期维护：独立于上游，更自主

阶段 2：SDL2 替换策略（二选一）

方案 A-1：为 SDL2 写 OpenHarmony 后端（推荐）

推荐理由：虽然工作量大（约 3-5K 行 C），但收益最高 —— 可提交 SDL2 上游，后续 SDL 升级无负担，其他项目也能复用。参考 SDL2 的 Android/RPi 后端实现。
SDL2 子系统需实现的 API映射到鸿蒙 API估测行数
VideoSDL_CreateWindow、SDL_GL_CreateContext、SDL_Vulkan_CreateSurface、SwapBuffersOH_NativeWindow + EGL~1,500
EventSDL_PollEvent、触摸/键鼠事件转换OH_TouchEvent / OH_KeyEvent / OH_MouseEvent~800
AudioSDL_OpenAudioDevice、回调音频OH_AudioRenderer~400
ClipboardSDL_SetClipboardText / Get需 NAPI 桥接~200
其他File IO、JNI 等应用沙箱路径~300

方案 A-2：写 SDL2→鸿蒙 垫片层（快速但耦合）

权衡：在 src/engine/client/ 下新建 backend_harmonyos/，直接把 SDL2 调用映射到鸿蒙原生 API。改动集中在 input.cpp、backend_sdl.cpp、sound.cpp、client.cpp。速度快但与鸿蒙 API 耦合，后续维护成本高。

推荐决策

核心推荐：分两步走

短期（3 个月内）：C++ QmClient 移植鸿蒙，写 SDL2 OpenHarmony 后端，走 GLES 3.x，出可玩手机版。

长期（并行）：关注 ddnet-rs 进展，等它功能补完 + winit/ash 鸿蒙支持成熟后，再考虑切换到 Rust 版本。

      ├─ 短期用 C++ 版满足需求
      ├─ 长期等 ddnet-rs 成熟后切换
      └─ SDL2 后端可作为 Rust 版 winit 后端的参考

关键风险清单

风险影响缓解措施
SDL2 鸿蒙后端工作量大推迟出包时间先用垫片层（A-2）快速验证，再逐步替换为正式后端（A-1）
鸿蒙 GLES 驱动兼容性问题渲染异常准备 Vulkan 后端作为备选；参考鸿蒙官方游戏适配指南
Rust 鸿蒙交叉编译不可用影响 Rust 桥接模块评估是否可暂时禁用 Rust 桥接，纯 C++ 编译
鸿蒙手柄 API 缺失蓝牙/USB 手柄不可用PC 模式下通过 HID 接口自行实现；手机端暂不支持
应用商店审核上架延迟提前了解审核规则，准备合规材料

需要进一步调研的项

  1. 鸿蒙 NEXT 手柄/Game Controller 原生 API 是否存在
  2. openssl / libcurl 在鸿蒙 NDK 下的编译可行性
  3. 鸿蒙 POSIX socket 与 Linux socket 的差异点（setsockopt 选项、epoll 可用性等）
  4. Rust 编译到鸿蒙的自定义 target 可行性验证
  5. ddnet-rs 的 QUIC 协议是否有计划支持原始 DDNet 协议
