QmUi 组件 / 动画 / Theme 收口边界规格

本文只收口“怎么继续做 QmUi”，不把它写成全局 UI 重构计划。当前 QmUi 已有 runtime、动画、布局、tokens、theme、widget 原语和 dogfood，但仍与旧 CUI、局部动画 helper 并存，因此后续只能按单个组件族或单个 helper 迁移。

当前结论

项目状态口径
QmUi runtime已存在CGameClient 已持有 CUiRuntimeV2，并在重置/渲染阶段接入。
动画统一局部可统一QmAnim 和 QmAnimResolve 已提供统一动画 runtime，但局部 helper 仍在各组件中保留。
Theme / tokens半成品设计系统已有共享 token 和 light/dark IME theme，但不是完整 CSS-like 样式层。
全局 UI 替换不作为目标不能把 QmUi 直接写成全菜单、HUD、计分板的全局替换计划。
产品化路径明确优先选一个组件族或一个 helper 家族，先收口调用面，再扩散到下一块。

边界与非目标

本文的边界是“整理现有 QmUi 资产的使用规则”，不是“重新设计整个客户端 UI 架构”。如果未来要做系统级迁移，必须另开规格。
允许做不允许做
把新 QmClient UI 默认接到 QmUi tokens、theme 和 animation runtime。把所有旧页面一次性迁移到 retained/declarative tree。
在正在修改的组件里，把本地重复动画 helper 换成 QmAnimResolve 或 runtime 动画请求。为了统一而扫全仓库改所有局部 easing / tween helper。
逐个收口 widget 原语和 dogfood 页面中的重复样式。把 QmTheme 扩成完整全局换肤系统。
为新页面使用现有 tokens、motion level 和 icon/IME theme。把 UI 组件合并当成重构上游 DDNet 菜单的入口。

如果某个 UI 需求会同时触碰聊天、HUD、菜单、名字板和性能统计，那它已经超出本规格。

建议推进方式

  1. 先选一个当前正在动的 QmClient 组件族，比如设置页、资源页或 dogfood 页面。
  2. 只收口这个组件族内部重复的 1 个 helper 或 1 组 token 用法，不碰其他页面。
  3. 如果这个组件族里已有局部动画 helper，再考虑替换成 QmUi 动画 runtime。
  4. 等两个以上组件族都稳定使用同一套 token / motion 习惯，再回头讨论更大的 Theme 层整理。

这样做的目的不是保守，而是避免把“统一”做成一次性全局迁移。QmUi 当前更适合按使用场景逐步收口。

高频接触点

入口观察到的现状后续口径
menus_qmclient.cppdogfood 模式已把 QmUi context 和 animation runtime 接进设置页。这是最适合做组件收口的入口之一。
chat.cpp聊天页仍存在局部 easing helper，不是完整 QmUi 化。只在聊天页被修改时再谈迁移，不做横向扫面。
hud_notifications.cppHUD 通知也有局部动效实现。可作为动画统一的第二批候选，但不合并到本次范围。
UiTokens.h / QmTheme.h共享 token 和 theme 已存在。优先作为新页面默认入口，而不是强制回写老页面。
