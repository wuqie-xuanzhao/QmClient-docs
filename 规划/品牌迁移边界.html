Qimeng 到 QmClient 品牌迁移边界规格

本文接管旧清单里的“品牌化迁移 Qimeng -> QmClient”。当前代码已经大量使用 QmClient / QMCLIENT / qm_，但仍保留 Q1menG 识别链路和少量历史注释；因此后续不能做全局替换，只能按“用户可见品牌、配置兼容、远端服务协议、历史内部标识”分层处理。

当前结论 迁移分层 非目标 建议阶段 复核证据

当前结论

范围状态维护口径
用户可见 UI 品牌主线已是 QmClient设置页、配置文件入口、配置筛选和若干模块标题已显示 QmClient。
配置域 / 保存路径已是 QMCLIENT / QmClientConfigDomain::QMCLIENT 保存到 QmClient/settings_qmclient.cfg，并保留旧根路径迁移。
新配置命名规则明确新增 QmClient 配置使用 qm_ / Qm，不再写 config_variables_qimeng.h、QIMENG 或 qmc_。
Q1menG 识别链路历史内部名仍在ClearQ1menGSyncMarks()、MarkQ1menGSyncClient() 和数组成员仍在识别/远程粒子链路中，不应无计划改名。
远端服务 / 包名 / 文件名需单独评估更新 URL、qmclient 数据目录、/qm/* 服务路径和发布包名不能跟 UI 文案一起改。

迁移分层

层级可以推进需要谨慎
用户可见文字把旧文档和新增 UI 文案统一写成 QmClient。不要把服务端协议、日志字段、存档文件名一起重命名。
配置与文件路径新文档统一引用 ConfigDomain::QMCLIENT 和 QmClient/settings_qmclient.cfg。现有用户 cfg 需要 legacy 路径和兼容策略，不能删除旧迁移入口。
源码内部命名新代码使用 QmClient、Qm、qm_。Q1menG 识别函数与数组要等专门重构任务处理，避免破坏远程识别和粒子展示。
远端服务和发布链路文档可以标明当前 /qm/* 命名空间和 GitHub release URL。不要在纯文档整理中改变中心服接口、User-Agent、更新 URL、包名或数据目录。

非目标

  • 不做全仓库 Q1menG / Qimeng 文本替换。
  • 不删除 settings_qmclient.cfg legacy 迁移路径。
  • 不把 qmclient 数据目录、GitHub release URL、中心服 /qm/* 路径改名。
  • 不在没有迁移测试的情况下改配置变量脚本名。
  • 不把 DDNet/TClient 来源能力改写成 QmClient 原生能力。

品牌迁移最容易出错的是把“用户可见名字统一”误扩成“协议、文件、配置、远端服务全重命名”。这会破坏兼容性。

建议阶段

阶段内容验收
P0 文档收口所有新版 HTML 文档引用当前 QMCLIENT、QmClient/、qm_ 规则，并把旧 Qimeng 口径标为历史。文档链接检查和 check_docs.py 通过。
P1 用户可见文案审计只审计 UI 文案、设置页标题、帮助文本和文档，不改配置脚本名。新增一页文案清单或小补丁，附截图/翻译生成验证。
P2 内部命名重构提案如果确实要改 Q1menG 识别链路，先写影响面：函数、数组、中心服报告、远程粒子、badge。有迁移计划、测试点和回滚策略后再动源码。
P3 服务/包名迁移更新 URL、User-Agent、数据目录或 release 包名属于发布链路任务。需要服务端、发布包、自动更新和用户数据迁移一起验证。
