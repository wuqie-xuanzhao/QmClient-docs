跨服务器全局聊天边界调研

本文把“跨服务器全局聊天”从好友系统小改里拆出来：当前代码只有服务器内聊天、好友通知和进服问候；真正跨服聊天需要中心服务、身份、权限和滥用控制，不能直接复用当前聊天接口。

快速结论 当前事实 不要混淆的能力 可行阶段 真正实现前置条件 复核证据

快速结论

跨服务器全局聊天当前不是已实现能力，也不应作为“好友分类/好友提醒”的小范围增强来做。它至少需要一个独立的中心服务或协议层，以及身份、认证、限流、举报/屏蔽、隐私和兼容性设计。

问题结论可信度
当前 global 聊天是否跨服务器？否。当前 Team=0 global 是当前服务器内全服频道。高
好友上线提醒是否等于 presence 系统？否。它基于服务器浏览器 HTTP 列表扫描，不提供可靠账号在线状态。高
当前好友身份能否支撑跨服全局聊天？不足。好友模型以 name + clan 为核心，没有唯一账号 ID。高
是否可以直接调用 CChat::SendChat() 实现跨服聊天？不可以。该接口面向当前服务器连接，不能绕过协议和服务端边界。高

当前事实

  • QmClient 当前聊天组件把消息发送到当前服务器连接，频道语义仍是服务器内 global/team/whisper。
  • 好友系统当前是 name + clan + category + note 的本地模型，不是账号系统。
  • Qm 好友上线提醒通过刷新/扫描服务器列表来判断好友是否出现在某个服务器。
  • Qm 好友进服问候只在当前服务器玩家列表变化时触发，并向当前服务器聊天发送问候文本。
  • 代码检索没有找到可证明跨服聊天已实现的 GlobalChat 组件、独立 socket、中心协议或服务端入口。

这意味着旧文档里的“好友分类 / 全局聊天”必须拆成两条线：好友分类和好友提醒是当前能力；跨服务器全局聊天是高风险规划/调研项。

能力真实范围不能推导出的结论
服务器内 global chat同一服务器里的所有玩家频道。不能说明客户端有跨服消息总线。
好友上线提醒从服务器浏览器列表中发现好友名/战队。不能说明有账号身份、在线状态订阅或私信能力。

可行阶段

阶段目标边界
P0 文档边界把跨服全局聊天从好友系统里拆出，避免误判为已实现或低成本任务。只改文档，不改源码。
P1 本地好友活动流如果需要更强好友体验，可先做本地“好友在哪些服务器出现过/最近上线”信息面板。仍基于服务器浏览器扫描；不发送跨服消息，不做账号系统。
P2 中心服务调研评估是否需要 QmClient 自有服务、登录身份、消息通道、审核和安全模型。先写服务与协议调研，不直接嵌入客户端 UI。
P3 实现规格只有在中心服务、身份和滥用控制明确后，才写客户端实现规格。必须获得协议/服务端/隐私边界批准。

真正实现前置条件

  • 身份：明确玩家唯一身份来源，不能只依赖可变的 name + clan。
  • 认证：明确客户端如何登录、如何防止冒名和重放。
  • 服务：明确是否自建中心聊天服务、如何部署、如何降级。
  • 协议：明确消息格式、版本兼容、错误处理和断线重连。
  • 滥用控制：至少需要限流、屏蔽、举报、管理员处理和日志策略。
  • 隐私：明确默认开关、可见范围、好友关系是否暴露、是否记录聊天内容。
  • 兼容性：不得把跨服聊天伪装成 DDNet 服务器内消息，也不得要求普通服务器改协议。

在这些前置条件未定义前，不应新增“跨服发送”按钮、自动跨服问候、匿名全局广播或把本地好友提醒扩展成消息系统。
