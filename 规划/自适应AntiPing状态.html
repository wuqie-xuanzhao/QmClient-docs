自适应 AntiPing 现状与风险

本页接管旧 adaptive-antiping-plan.md。旧案可以保留“基于网络状态给出建议”的方向，但不能直接按“自动改 cl_antiping_percent / cl_antiping_limit”实现；当前代码已有 AntiPing、TClient 平滑、预测 margin 自动补偿和网络监控显示，预测行为属于高风险范围。

旧计划修正

旧判断当前修正
缺少网络状态显示，需要新增 Network HUD。已过时。状态栏和 QmMonitoring 已经能显示 latency、prediction、jitter、packet loss、connection grade；后续应复用现有显示，而不是新建平行 HUD。
直接根据 ping 自动调整 cl_antiping_percent / cl_antiping_limit。风险过高。AntiPing 影响预测、其他玩家位置、武器/投射物表现和冻结场景；自动改写配置会影响用户预期和回归定位。
新增 cl_antiping_adaptive 等配置。不适合 QmClient 新功能命名。若未来确实新增 QmClient 配置，应使用 qm_ / Qm 前缀，并明确不改变上游语义。
AntiPing 相关配置在 config_variables_qmclient.h。基础 AntiPing 配置实际在 src/engine/shared/config_variables.h。QmClient/TClient 扩展运行时存在，但本轮未把所有 TClient 配置定义位置完整展开。

建议后的最小规划

阶段范围验收点
P0 只读建议基于 QmMonitoring / status bar 指标给出“建议检查 AntiPing 设置”的只读提示。不自动改配置；只显示当前 latency、jitter、packet loss 与可能原因。
P1 预设推荐提供手动应用的配置预设，用户明确点击后才写入。写入前展示将变更的配置项，并保留恢复路径。
P2 弱网验证用 fake latency / jitter / packet loss 或可复现实验脚本记录行为。有低 ping、高 ping、高 jitter、packet loss、冻结场景和 demo 回放边界证据。
P3 自动模式调研如果仍要做自动模式，先写独立规格并审查预测兼容性。默认关闭；有频率限制、用户可见状态、日志和回退开关。

不建议把“自动调参”作为第一步。更稳妥的落点是“诊断和建议”，因为当前项目已经有足够的网络指标可用，而预测参数本身直接影响玩法体验。
