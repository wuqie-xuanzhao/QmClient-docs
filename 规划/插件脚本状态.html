脚本与插件系统现状

本页接管旧 plugin-script-system-plan.md。当前 QmClient 已有 ChaiScript 手动执行能力，但没有完整插件目录、插件管理 UI、权限模型、自动加载或 Lua 方案；旧计划不能直接执行。

当前已存在的能力

领域状态当前实现说明
脚本引擎implemented客户端组件中接入 CScripting，控制台命令为 chai，执行 ChaiScript 脚本文件。旧文档“没有完整脚本解释器”的结论已过时；当前方向不是 Lua。
脚本 APIlimitedexec(string) 执行控制台命令，echo(string) 输出到客户端，state(name, arg?) 读取有限客户端状态。exec 权限很宽，任何扩展都必须先处理安全和公平性边界。
状态查询implementedstate 支持 game mode、地图、服务器名/IP、玩家人数、队伍、dummy、rcon、社区、地理位置和玩家 name/clan/id 查询。适合只读脚本辅助，不应直接推导成自动化插件平台。
运行环境implementedChaiScript 使用 No_Load_Modules 和 No_External_Scripts，注册 print/puts、include(path)、file_exists(path)、re 和 math 命名空间。include 与 file_exists 使用 QmClient storage 路径，仍需文档化允许读取范围。
聊天绑定implementedbindchat 在 src/game/client/components/tclient/，配置域为 QmClient/qmclient_chatbinds.cfg。旧文档把路径写到 qmclient/bindchat.cpp，这是错误的。
绑定轮盘implementedbindwheel 同样位于 src/game/client/components/tclient/，保存回 QmClient 配置域。它是命令绑定扩展，不是插件系统。
插件平台not implemented本轮未看到 plugins/ 目录约定、plugin.json、插件管理 UI、权限分级、沙箱策略、反作弊标记或自动加载。旧文档的插件目录和 Lua 插件管理设计仍只是未验证草案。

旧计划修正

旧计划点当前判断处理方式
推荐集成 Lua 作为脚本引擎。不符合现状当前已有 ChaiScript 和 chai 命令。除非重新做技术选型，不应同时引入第二套脚本引擎。
缺少脚本引擎，需要从零开始。已过时应改为“已有手动 ChaiScript 能力，但 API、权限和文档不足”。

新增 cl_plugins_* 配置。命名错误QmClient 新配置必须使用 qm_ / Qm 命名口径；但当前不建议新增插件开关配置。
把 bindchat/bindwheel 当作插件参考实现。需改写它们可以作为命令绑定 UI/配置参考，但不是脚本权限或插件生命周期参考。
插件使用标记和服务器端反作弊检测。超出当前证据本轮未看到协议或服务端配套能力；默认不要触碰协议、玩法语义或远端标记。

风险边界

脚本系统当前最大的边界不是“如何支持更多 API”，而是 exec 已能执行任意控制台命令。任何新增自动加载、输入模拟、文件写入、网络访问、插件市场或 UI 热加载，都会把公平性和安全风险放大。

  • 默认只把当前 ChaiScript 视为显式手动执行工具，不把它宣传成通用插件平台。
  • 默认不新增自动运行脚本、不新增输入模拟 API、不新增文件写入 API、不新增网络 API。
  • 默认不触碰协议、服务端检测、demo/回放格式或玩法语义。
  • 如果要继续推进，先做只读状态查询、脚本示例、错误提示和文档化边界。
